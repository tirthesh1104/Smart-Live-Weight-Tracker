3. Data Flow & Architecture

The system operates a multi-tier data flow combining client-side reactive state, REST/PostgREST database persistence, and browser local storage:

  1. Data Ingestion Stage: Telemetry originates from the software simulation engine (SensorSimulator.tsx), manual administrative entry, or commuter check-in forms. Physical load cells are software-simulated.
  2. Processing & Validation Engine: Raw weights in kg are converted synchronously into net payload, clamped occupancy percentages, and safety hazard states via weightCalculations.ts.
  3. State Distribution & Persistence: TrainContext dispatches state updates across all listening components. When connected to Supabase, mutations sync to remote tables; otherwise, state falls back to versioned localStorage (slwt_trains_v2).
  4. Presentation Layer: Frontends render color-coded coach cards, platform pillar advice (Pillars 1–6, 7–12, 13–18), SVG rake side-elevations, and LED-styled station boards.

4. Algorithms & Prediction Logic

All mathematical formulas, classification thresholds, and forecasting models implemented in weightCalculations.ts and aiClient.ts are strictly detailed below:

A. Net Passenger Payload & Occupancy Percentage

Payload Capacity = max(1, Max_Capacity_Kg - Empty_Weight_Kg)
Net Passenger Payload = max(0, Current_Weight_Kg - Empty_Weight_Kg)
Raw Occupancy % = (Net Passenger Payload / Payload Capacity) * 100
Clamped Occupancy % = min(100, max(0, round(Raw Occupancy %, 1)))

B. Structural Hazard & Occupancy Classification Thresholds

  • Overloaded (Status: 'overloaded'): Triggered when Current_Weight_Kg > Max_Capacity_Kg. Excess Weight = Current_Weight_Kg - Max_Capacity_Kg.
  • Full / Heavy (Status: 'full'): Triggered when Current_Weight_Kg <= Max_Capacity_Kg AND Raw Occupancy > 75%.
  • Moderately Crowded (Status: 'moderate'): Triggered when 40% < Raw Occupancy <= 75%.
  • Space Available (Status: 'available'): Triggered when Raw Occupancy <= 40%.

C. Passenger Count Estimation Formula

Estimated Passenger Count = round(Net Passenger Payload / 78 kg)

D. AI Coach Recommendation Selection

Filters out non-passenger stock (coach_type != 'Engine' AND coach_type != 'Pantry Car'). Sorts by occupancy_percentage ascending. Identifies the coach with the lowest bogie suspension strain.

E. Time-Series Crowd Forecasting (15, 30, and 60-Minute Horizons)

Step Multiplier = Horizon_Minutes / 15
Rush Factor = 1.4 if Rush Hour else 1.0
Base Surge = 380 kg (if General Class) else 180 kg
Projected Weight = min(Max_Capacity * 1.15, max(Empty_Weight, Current_Weight + (Base Surge * Step * Rush Factor)))
Projected Occupancy % = round(((Projected Weight - Empty_Weight) / Payload Capacity) * 100, 1)
Confidence: 15 min = 0.92 | 30 min = 0.84 | 60 min = 0.73

5. System Performance & Technical Metrics

  • Telemetry Polling Cadence: Regulated by a 1000ms setInterval with a 3-second auto-refresh counter (autoRefreshCounter) updating state in memory without full-page reloads.
  • Client Caching & Offline Resilience: Storage keys (slwt_trains_v2, slwt_notifications_v2, slwt_incidents_v2) maintain version isolation. If remote Supabase endpoints fail, the app switches to local storage seamlessly.
  • Database Indexing & Integrity: Optimized B-Tree indexes on coaches(train_id), weight_readings(coach_id), weight_readings(recorded_at DESC), and notifications(is_read). Enforces UNIQUE(train_id, coach_no) and UNIQUE(coach_id, seat_number).
  • Security Verification: Salted SHA-256 PIN hashing with rate-limited attempt counters. PostgreSQL trigger public.protect_profile_role() blocks unauthorized self-elevation in public.profiles.
